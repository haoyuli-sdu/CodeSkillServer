## Overview

`oapi-codegen` turns an OpenAPI spec into a Go client (typed request/response
structs + a `Client` with one method per operation). This skill covers the
whole pipeline: adding the tool, laying out packages, wiring `go:generate`,
and the two gotchas that actually bite (stale specs, duplicate package docs).

**Default to one Go package per spec file**, not one merged package. Specs
from different products/services almost never share component definitions,
so merging risks type-name collisions for no benefit. Only merge if the specs
were authored as a single unified document (shared `$ref`s across files) —
confirm that before combining, don't assume it.

---

## Step 1: Add oapi-codegen as a tool dependency

Go 1.24+ supports the `tool` directive in `go.mod` — no `tools.go` boilerplate needed:

```sh
go get -tool github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen
```

This adds a `tool` line to `go.mod` and pulls in the codegen tool's own
dependency tree. `go generate` (see Step 4) resolves it automatically via
`go tool oapi-codegen`.

---

## Step 2: Get the specs into a stable, checked-in location

**Never wire codegen directly at a gitignored or ephemeral output
directory** (e.g. a scraper's `./out`, a CI artifact path). Anyone who clones
the repo needs `go generate` to work without first re-running whatever
produced the specs. Copy them into the repo proper:

```sh
mkdir -p sdk/<product>/openapi
cp <wherever-the-specs-landed>/*.json sdk/<product>/openapi/
```

If specs need periodic refreshing from a live source, document that refresh
command in the README (fetch → copy into `openapi/` → `go generate`) rather
than making generation depend on the fetch step directly.

---

## Step 3: Lay out one package per spec

For each spec file, derive a Go-safe package name (strip the file extension
and any `-api`/`.json` suffix, remove hyphens — e.g. `billing-product-api.json`
→ `billingproduct`). Create:

```
sdk/<product>/<pkgname>/
    oapi-codegen.yaml   # config
    generate.go         # go:generate directive
    client.gen.go        # generated — do not hand-edit, do not write yet
```

**`oapi-codegen.yaml`** — check the field names for the installed version
first (the config schema has changed across major versions):

```sh
go tool oapi-codegen -package <pkgname> -generate types,client -output-config <any-spec-file>
```

That prints the config this exact version expects. As of oapi-codegen v2.8,
it's:

```yaml
package: <pkgname>
generate:
  client: true
  models: true
output: client.gen.go
```

**`generate.go`**:

```go
package <pkgname>

//go:generate go tool oapi-codegen -config oapi-codegen.yaml ../openapi/<spec-file>
```

**Gotcha — do not add a package doc comment to `generate.go`.**
`client.gen.go` gets one automatically (`// Package <pkgname> provides
primitives to interact with the openapi HTTP API. // Code generated by
... DO NOT EDIT.`). A second package-doc comment on `generate.go` trips
`godoclint`'s "package has more than one godoc" check. If you want context in
`generate.go`, write a **plain** (non-doc) comment — put it after `package
<pkgname>` or use a form that isn't directly above the `package` line.

---

## Step 4: Generate and fix up dependencies

```sh
go generate ./sdk/...
go mod tidy   # generated code imports github.com/oapi-codegen/runtime — a
              # real dependency, not just a tool one; go.sum needs it too
go build ./...
go vet ./...
```

`go mod tidy` is not optional — skipping it leaves a `no required module
provides package github.com/oapi-codegen/runtime` build failure.

---

## Step 5: Wire a regeneration command

Add a task/make target so this isn't a one-off:

```yaml
# Taskfile.yml
generate:
  desc: Regenerate the <product> client SDK from its checked-in specs
  cmd: go generate ./sdk/...
```

---

## Step 6: Check project-wide lint/arch tooling against the new code

Generated files carry the standard header (`// Code generated by ... DO NOT
EDIT.`), which most tooling already knows to skip — but verify, don't assume:

- **golangci-lint**: confirm `formatters.exclusions.generated: lax` (or
  equivalent) is set, so gofmt/gofumpt/golines don't try to reformat
  generated output.
- **nilaway**: pass `-exclude-file-docstrings "Code generated"` if not
  already in the lint command.
- **go-arch-lint** (or similar package-boundary linters): the new `sdk/`
  tree needs its own component entry or every generated file gets flagged as
  "not attached to any component." Add it as a **leaf** component (depends on
  nothing internal; nothing internal depends on it, at least until something
  actually imports the SDK):

  ```yaml
  components:
    sdk: { in: sdk/** }
  deps:
    sdk: { mayDependOn: [sdk] }
  ```

  If the project's arch-lint config is documented as "frozen" from an earlier
  refactor plan, adding a genuinely new, unrelated component afterward is a
  legitimate evolution — not a violation of that freeze. The freeze was about
  not deviating from that specific plan's scope while implementing it.

Run the full lint suite once (`golangci-lint run`, `go-arch-lint check`,
`nilaway`, whatever the project uses) before calling this done — new
generated code is exactly the kind of thing that trips a linter no one
thought to configure for it.
